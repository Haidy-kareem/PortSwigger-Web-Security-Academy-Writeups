## 1. Lab Overview

This lab demonstrates a **Referer-based access control vulnerability**.

The application contains an administrative function that allows administrators to promote users to administrator.

The intended behavior is:

- Only authenticated administrators should be able to access the administrative functionality.
- Requests to sensitive administrative endpoints should be authorized based on the user's actual privileges.

However, the application incorrectly relies on the HTTP `Referer` header to determine whether the request originated from the administrator panel.

Since the `Referer` header is controlled by the client, it can be modified by an attacker.

### What is the `Referer` header?

The `Referer` header tells the server which page the request supposedly came from.

For example:

```
Referer: https://example.com/admin
```

This tells the server that the request was supposedly initiated from `/admin`.

The problem is that **the client can modify this header**.

Therefore, a server should never treat:

```
Referer: /admin
```

as proof that the requester is actually an administrator.

The important part here is:

```

```

So I was **not actually an administrator**, but I made the request appear as though it originated from the administrator page.

# 5. Exploitation

I sent the modified request through Burp Suite Repeater.

The server accepted the request and returned:

```
HTTP/2 302 Found
Location: /admin
```

This indicated that the request had been processed successfully.

The key point is that the server accepted the administrative action even though the request was authenticated using **Wiener's normal-user session**.

This confirmed that the application was incorrectly trusting the `Referer` header as part of its access control mechanism.

# 7. Vulnerability Explanation

The vulnerability exists because the application uses the `Referer` header as an authorization mechanism.

The application effectively assumes:

```
Referer = /admin
        ↓
Requester came from Admin Panel
        ↓
Allow administrative action
```

But this assumption is incorrect.

The `Referer` header is **client-controlled** and therefore cannot be trusted as proof of authorization.

An attacker can simply send:

```
Referer: https://target.com/admin
```

while using their own normal-user session.

The server should instead determine authorization from the authenticated user's privileges on the server side.

---

# 8. How to Prevent It

The `Referer` header should **never be used as an authorization mechanism**.

Authorization should be performed server-side based on the authenticated user's actual permissions.

For example:

```
Request
   ↓
Identify authenticated user
   ↓
Check user's role/permissions
   ↓
Is user authorized?
   ├── Yes → Perform action
   └── No  → Reject request
```

The application should not make authorization decisions based on:

```
Referer
```

or other client-controlled values.

A secure implementation would verify that Wiener's account actually has administrator privileges before allowing:

```
GET /admin-roles?username=wiener&action=upgrade
```

# Notes

> **Never trust the `Referer` header for access control.**
> 

The important lesson from this lab is not simply "change the Referer."

The real methodology is:

1. **Explore the normal application flow.**
2. **Identify sensitive/privileged requests.**
3. **Understand which parameters and headers are involved.**
4. **Repeat the request using a lower-privileged session.**
5. **Test whether client-controlled values such as `Referer` affect authorization.**
6. **Verify whether the privileged action is actually performed.**
